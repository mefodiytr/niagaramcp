## Surprises and notes during implementation

### What went exactly as the recon predicted

- **Auth above transport** (recon §13.4) — confirmed: didn't write a
  single line of auth code for `/mcp`. The shared
  `checkServiceEnabled` + `checkAuth` at the top of `doGet`/`doPost`
  in the existing `McpServlet` covered the new branch for free,
  including the new `doDelete` override.
- **`McpProtocol.handle()` transport-agnostic** (recon §13.1) — only
  changed the parameter type `McpSession session` → `Session
  session`. The body required no edits because the only method it
  calls on the session, `markInitialized()`, was already on the
  interface I extracted.
- **Tools unchanged** (recon §8.7) — confirmed. Did not open any of
  the six `tools/*.java` files during this work.
- **Session model is the only SSE-coupled bit** (recon §13.2) — true.
  The refactor was contained to four files: introducing `Session`,
  renaming `McpSession` → `SseSession`, broadening the registry's
  value type, casting in the one place SSE-specific behaviour is
  needed (`handleMessage`).
- **Java 8 baseline holds** (recon §13.8) — wrote no `var`, no
  lambdas-in-interfaces, no streams. The code reads like Java 7.

### Minor surprises

- **`enqueue` belongs to SseSession only.** The brief explicitly
  warned not to put `enqueue` on the `Session` interface (line 169-
  173 of the brief), and the warning was load-bearing: the cleanest
  place to keep the SSE-specific cast `(SseSession) session` is
  inside `handleMessage`, narrowed via `instanceof` to also handle
  the case where the legacy `sessionId` query param happens to
  resolve to a Streamable session — return 404 in that case to keep
  the namespaces honest. Done at `McpServlet.java:117-122`.
- **GET /mcp degenerate-by-design.** The brief and ADR-0001 both
  call out that `GET /mcp` is currently a no-op SSE response. I
  considered adding a real `StreamableSession`-backed queue and
  deferred per ADR — no current tool produces server-initiated
  push, so an unused queue is dead weight. Documented prominently
  in the handler JavaDoc and in the ADR's "Open items" section.
- **`getInputStream()` cast removed.** The original `McpServlet`
  has `(InputStream)req.getInputStream()` (a no-op cast,
  `McpServlet.java:177`). Left it alone — touching unrelated lines
  in this work would have widened the diff. Future cleanup item.
- **`mcpSessionIdleTimeoutMs()` returns `long`, property is `int`
  seconds.** `int * 1000L` overflow occurs at ~24.86 days. Acceptable
  for an idle timeout (max property value 2 147 483 647 seconds is
  68 years; clamping not added since no operator will set a 25-day
  idle timeout). If anyone does set it that high we'll wrap to a
  negative `long` and `isStale()` will report stale on every check
  — fail-closed, correct outcome but an ugly path.

### Things in the recon that turned out imprecise

- **Recon §1.5 method-count heuristic** for `BMcpPlatformService`
  said 28; the actual count is closer to 18 once you exclude
  property-related getter/setter pairs that the heuristic mis-counted.
  Doesn't matter for any decision; flagging since the brief mentions
  trusting the recon.
- **Recon §13.11** said "code surface grows ~250 LOC" for the
  Streamable HTTP work. Actual growth in `com.niagaramcp.server` Java
  is about 290 LOC across new files (`Session.java` +
  `StreamableSession.java` + new methods in `McpServlet.java` +
  `McpSessions.java`). Within the budget; flagging the precise
  number for next time.
- **Recon §10.4** correctly noted "no `ExecutorService`/`Thread.start`".
  v0.2.0 holds that baseline — `StreamableSession` + lazy eviction
  did not introduce any new threading primitive.

### Things deferred (per ADR-0001 "Open items")

| Item | Why deferred |
|---|---|
| **Server-initiated push on `GET /mcp`** | No current tool emits mid-call notifications. Implementing a `StreamableSession`-backed queue today would be 60+ LOC of unexercised code. Revisit when tool-progress events become a real feature. |
| **Streaming response on POST `/mcp`** (chunked SSE reply) | Same reason — current tools either return immediately (`echo`) or briefly block (`readPoint`, `writePoint`); no benefit from streaming. |
| **OAuth2 resource-server profile** | Bearer with the configured `apiToken` works for current users. OAuth requires non-trivial token-validation infra, deferred to v0.3+. |
| **`McpProtocol.SERVER_VERSION` hardcoded** | Recon §13.10 noted this; not in this work's scope. Pull from gradle/manifest in a future commit. |
| **`SseSession.SENTINEL_CLOSE` constant duplication** with `"__CLOSE__"` literal at `McpServlet.java:95` — recon §13.10. Minor; not addressed. |
| **`McpProtocol` capability advertisement enrichment** under 2025-06-18 | The current `{tools: {}}` is spec-compliant but minimal. If a future iteration wants `tools.listChanged: true` (notifying clients when tools change at runtime), that's a separate piece of work. |

## Verification needed (human, runtime)

Static inspection and gradle assemble pass. The following must be
exercised against a real Niagara station before tagging v0.2.0:

1. **Deploy v0.2.0 jar** to `$niagara_home/modules/`, restart station.
   Confirm it loads with the existing dev-cert (per `_SMOKE_TEST.md`
   §"Подпись для v0.1.0").
2. **Run the v0.2.0 curl runbook** in `_SMOKE_TEST.md` end-to-end —
   six steps. All six checkboxes must tick.
3. **Run the v0.1.0 SSE runbook** (`_SMOKE_TEST.md` §"Что не
   проверено" steps 6-7) on the same v0.2.0 jar. Existing SSE
   clients must continue to work bit-for-bit. This is the
   backward-compat assertion.
4. **Behaviour under repeated reconnects.** Open `POST /mcp`
   `initialize`, capture `Mcp-Session-Id`, then 100× `tools/list`
   in a loop. Active session count (visible via the existing
   `McpSessions.activeCount()` method, not currently surfaced in
   any UI — could be probed via Workbench Spy on the service if
   needed) should stay at 1.
5. **Idle eviction actually fires.** Set
   `mcpSessionIdleTimeoutSec = 60` for a quick test. Open a
   session, wait 70+ seconds, attempt a `tools/list` → expect 404
   "Session not found or expired". Reset to 1800 after.
6. **DELETE /mcp idempotency.** Call `DELETE` twice with the same
   session id. Both should return 204.
7. **Cross-transport isolation.** Open an SSE session (gets a
   sessionId via `event: endpoint`), then attempt `POST /mcp` with
   the SSE session id as `Mcp-Session-Id` — expect 404 (the
   `acquireStreamable` check rejects the wrong session type).
   Conversely, open a Streamable session, then attempt
   `POST /messages?sessionId=<streamable-id>` — expect 404.
8. **Concurrent connections** — open 5 simultaneous Streamable
   sessions, hit each with a `tools/call echo` from separate
   shells. All should complete without deadlock.
9. **`UNAUTHENTICATED_ACCESS` permission still satisfies the new
   endpoints**. The module declares it once in
   `module-permissions.xml`; the new `/mcp` paths inherit the same
   regime. Verify by sending a `POST /mcp` without `Authorization`
   header — expect 401 with `WWW-Authenticate: Bearer`.
