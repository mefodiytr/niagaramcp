## Surprises during implementation

### sessionCount mechanism — chose notification, not tick()

The brief recommended `BService.tick()` as the canonical mechanism
for periodically refreshing `sessionCount` from
`McpSessions.activeCount()` without spawning a thread. Instead,
went with a **static-notification approach**: `McpSessions` calls
`BMcpPlatformService.refreshSessionCount()` from inside
`createSse()`, `createStreamable()`, `remove()`, `closeAll()`, and
the lazy-eviction branch of `acquireStreamable()`.

Reasons:
- **Exactness.** `tick()` runs on a Niagara framework cadence
  (something like 1 sec by default); the property would always lag
  by up to a tick. Notifications make it instantaneous.
- **Same baseline preserved.** No new threads, no change to the
  framework's own scheduling — the notification is a synchronous
  in-process method call from the same thread that mutated the
  registry.
- **Simpler shutdown.** No need to deregister a tick handler; when
  `INSTANCE` becomes `null` in `serviceStopped()`, the helper
  no-ops cleanly.

Trade-off: tied McpSessions to BMcpPlatformService directly via a
static call. Seems acceptable for a runtime singleton — the same
pattern is already in use for `apiToken()`, `mcpProtocolVersion()`,
etc.

### `:assemble` post-jar copy still fails

The recurring environment issue — Gradle's auto-install task tries
to copy the new jar over `$niagara_home/modules/niagaramcp-rt.jar`,
but the running station holds a write-lock. Worked-around as in
v0.3.0/v0.3.1: `:compileJava` for per-commit verification, `:jar`
to inspect the artifact (the jar is built before the copy fails).
Operator just needs to stop the station before final replacement.

### BFilePath investigation outcome

Per brief commit 3: dug into baja.jar (4.15.3.28) for a
filesystem-path BSimple type. Found: `javax.baja.file.FilePath`
(plain util class, not a `BIDataValue`), `BAbstractFile` (in-station
file space only), no `BFacets.FILE_BROWSE` key. Per the brief's
"When to stop and ask" clause, accepted `String` and documented the
finding inline on the property javadoc (19 LOC) so the next agent
doesn't repeat the dig.

### Smoke client baseline was 22 not 24

Brief said "Total: 24 → 26 steps" — actual baseline was 22 steps
(grep confirmed: step(1) through step(22)). Added steps 23 and 24,
new total **24**, not 26. Reflected in `_SMOKE_TEST.md` runbook
("smoke client 24 passed") and the implementation notes table
above. No functional impact — the brief was just miscounting from a
draft state.
