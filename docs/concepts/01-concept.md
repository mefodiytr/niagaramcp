# niagaramcp — Semantic Enrichment Layer (концепция)

## Проблема

Niagara station — это сырое дерево компонентов. Она знает, что
`Drivers/BACnet/Floor3/Bldg5/Sect4/T_AI_07` — это `BNumericPoint` с
фасетом `units=°C`. Она **не знает**:

- что это температура воздуха (vs температура воды/пара/масла);
- что это температура **на паркинге** (само слово "паркинг" в дереве
  не появляется, есть только `Floor3/Bldg5/Sect4`);
- что это **сектор E** (понятия "сектор" в Niagara нет, есть имя
  слота `Sect4`);
- что эта точка принадлежит конкретному оборудованию **AHU 1.1
  (руфтоп)**, а не висит сама по себе.

Без этого AI-агент не может ответить на вопрос "какая температура
на паркинге в секторе E" — у него просто нет mapping'а от
human-language к ord'ам.

## Стандартные подходы и почему они не работают на наших объектах

1. **Project Haystack tagging.** Open standard, в Niagara есть
   NHaystack module. Идеально, но требует, чтобы integrator при
   проекте навешивал теги — на типичном российском BMS-проекте
   этого нет.
2. **Строгий naming convention.** Парсить имена компонентов. Хрупко
   и не работает там, где naming разный.
3. **Manual Excel реестр.** Делается раз, устаревает мгновенно,
   никто не обновляет.

Все три требуют усилий **до того, как AI заработает**. Это
chicken-and-egg: пока модели нет, AI бесполезен; пока AI
бесполезен, никто не строит модель.

## Решение: AI bootstrap'ит модель сам, через walkthrough

Идея простая. У оператора/инженера, который настраивал станцию,
**знание уже есть** — в голове. Просто никогда не было удобного
способа его экстрагировать. AI становится этим способом:

1. AI проходит по дереву Niagara station сверху вниз.
2. Для каждого folder'а / equipment / точки задаёт уточняющий
   вопрос на естественном языке: "Я вижу 12 компонентов типа
   `BAhuController` под Drivers/BACnet/Roof. Это AHU? Где они
   физически расположены?"
3. Оператор отвечает: "Да, это руфтопы на крыше, 12 штук
   обслуживают разные зоны паркинга и торгового зала."
4. AI задаёт уточняющие вопросы про привязку каждого AHU к
   пространству, про aliases ("как ты их называешь в речи?"), про
   ключевые точки.
5. Каждая ответная единица знания **сохраняется в knowledge
   file** (структурированный YAML).
6. Knowledge file становится источником для Resources (см.
   соседний документ): AI грузит его при следующем conversation и
   уже имеет всю карту.

После одного walkthrough'а (1-2 часа на средний объект) AI готов
отвечать на вопросы вида "какая температура на паркинге сектор E"
без брожения по дереву.

## Что мы собираем во время walkthrough'а

Минимальный набор:

- **Spaces** — пространства (зоны, этажи, секторы): id, имя,
  aliases (как называют в речи), родительское пространство.
- **Equipment types** — типы оборудования: AHU, Chiller, Pump,
  VAV, FCU. Что считается AHU, какие у него ключевые слоты.
- **Equipment** — конкретные единицы: id, тип, имя, aliases,
  расположение (space), key points (с ролью — "это supply temp",
  "это return temp", "это compressor 1 status").
- **Point semantic roles** — роль точки внутри её equipment.
  `Drivers/BACnet/AHU_1_1/SAT` → "supply air temperature".

Расширенный набор (опционально, на следующих этапах):

- **Schedules** — расписания и какое equipment к ним привязано.
- **Alarm patterns** — типичные тревоги для типа оборудования.
- **Operating modes** — день/ночь/выходные.
- **Documentation links** — ссылки на проектную документацию,
  чертежи, спецификации.

## Где хранится knowledge

**Внешний YAML файл** в `${niagara_user_home}/niagaramcp/knowledge.yaml`
(точное имя/путь — см. [02-format.md](02-format.md)).

Решение в пользу external file vs Niagara native (Haystack tags
или BFacets):

- Не требует write permissions в станцию.
- Легко редактируется руками поверх AI-walkthrough'а.
- Можно version control'ить, копировать между объектами,
  использовать как шаблон ("AHU из АФИМОЛЛ как basis для
  АФИМОЛЛ-2").
- Не мутирует данные станции — снижает риск сломать что-то.

Минус — нужна синхронизация при переименованиях в Niagara. В
v0.3.0 решается через "rebuild" walkthrough — AI перепроходит
изменения с момента последнего snapshot'а и спрашивает только про
новое/перенесённое.

## Ценность

1. **AI впервые становится полезным на BMS-задачах.** Без
   semantic layer любой ответ — это либо абстрактные ord'ы, либо
   медленный brute-force через listChildren. С semantic layer —
   нормальный диалог про оборудование.

2. **Знание оператора капитализируется.** То, что раньше жило в
   голове и терялось при увольнении — теперь structured artefact,
   который можно передать, документировать, использовать в
   обучении новых сотрудников.

3. **Переиспользование между объектами.** Один раз размеченный
   AHU — шаблон для всех будущих AHU. Один раз размеченный
   паркинг — паттерн для всех паркингов.

4. **Knowledge file как side-deliverable BMS-проекта.** На
   commissioning AI прогоняется один раз, получаем YAML, прикладываем
   к проектной документации. Заказчик получает не только работающую
   станцию, но и AI-ready model.

## Связь с другими частями niagaramcp

Это **не отдельный продукт**. Semantic enrichment — это слой,
который питает остальные части:

- **Resources** (MCP) — knowledge file генерирует overview, equipment
  details, space resources. См. [04-roadmap.md](04-roadmap.md).
- **Prompts** (MCP) — pre-built prompts типа "Equipment state",
  "Zone comfort check" работают через resolved equipment id из
  knowledge file.
- **Search tools** — `findEquipment`, `findInSpace` ищут по aliases
  из knowledge file.
- **History/Alarms tools** — принимают человекочитаемое имя
  ("руфтоп 1.1") вместо ord'а, под капотом resolve через knowledge
  file.

## Не цели

- **Не заменяет** Project Haystack там, где он есть. Если станция
  уже tagged по Haystack — мы можем экспортировать knowledge file
  из тегов автоматически (отдельная фича, не v0.3.0 scope).
- **Не делает** автоматическую классификацию точек по AI без
  валидации оператора. Все assumptions AI задаёт как вопрос.
- **Не дублирует** Niagara station как source of truth для
  компонентов. Knowledge только обогащает: aliases, группировка,
  семантические роли. Сами components, ord'ы, текущие значения —
  всегда читаются из live station.
