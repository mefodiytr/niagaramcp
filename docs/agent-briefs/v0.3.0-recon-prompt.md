4.15.3 API surfaces and existing niagaramcp code. The plan is documented
in `docs/concepts/01-concept.md` through `04-roadmap.md`. Your job is to
confirm what's feasible, surface unknown costs, and produce a concrete

## Sections

### 1. Niagara History API surface (BHistoryExt)

Inspect what Niagara exposes for reading history. Look in:
- `javax.baja.history.ext` package
- `javax.baja.history` package
- `control-rt.jar` and `nre.jar` for related classes

Fill:
- The principal class (likely `BHistoryExt`) — full FQN, package
- Methods for reading historical records: signatures, parameter types,
  return types
- Time-range types: `BAbsTime`, `BRelTime`, `BTimeRange`?
- Record types returned: `BHistoryRecord` and subclasses
  (Numeric/Boolean/Enum/String). What fields each has (timestamp, value,
  status).
- Aggregation: does the API support server-side avg/min/max/count over
  intervals, or do we have to compute client-side?
- Pagination / large queries: any built-in limit?
- Discoverability: how to find which BControlPoint has a history
  configured (slot lookup? property?)
- Whether history can be queried by ord directly, or requires resolving
  to the history-extension component on the point

If anything's not knowable from static inspection, list as TBD with what
runtime experiment would resolve it.

### 2. Niagara Alarms API surface (BAlarmService)

Inspect:
- `javax.baja.alarm` package
- `BAlarmService`, `BAlarmRecord`, `BAlarmTransition` and friends

Fill:
- The service class — FQN, where to find the singleton
- Methods for current/active alarms (alarms not yet returned to normal):
  signatures, return types, filtering options (by source ord, severity,
  state, ack status)
- Methods for alarm history (historical alarm records): signatures, time
  range support
- AlarmRecord fields: timestamp, source ord, source name, message,
  severity, ack state, normal state, etc.
- How alarms relate to equipment in Niagara — are they attached to
  components (point fires alarm on threshold), or just events?
- Whether there's an event/listener mechanism we can use later for
  push notifications (out-of-scope for v0.3.0 but worth noting)

### 3. File system access from a module

The plan stores `knowledge.yaml` on disk. Determine how:
- How to obtain `niagara_user_home` path from inside a running module
  (likely `Sys.getNiagaraUserHome()` or similar)
- How to obtain station-specific home path if it differs
- What java.io.File operations are permitted from within a module
  given current `module-permissions.xml`
- Whether new permissions are needed (likely `FILE_ACCESS` with
  `paths="..."`). If yes — exact XML to add.
- Atomic write pattern compatible with Niagara — write to .tmp +
  rename, or any platform-specific concerns?
- Backup rotation: any helpers in baja for this, or we roll our own?

### 4. YAML parsing/emitting decision

The plan calls for YAML. Two paths:

**Path A: custom minimal YAML emitter** (~300 LOC).
- Identify what subset of YAML 1.2 our schema (`02-format.md`) actually
  needs: nested maps, lists, strings, ints, booleans, null. No anchors,
  references, multi-line block scalars, custom tags.
- Estimate LOC for a hand-written emitter+reader.
- Identify edge cases: strings with quotes, strings with leading
  whitespace, strings that look like numbers, unicode handling.

**Path B: use embedded `com.niagaramcp.json` library** (already in jar)
to store as JSON instead of YAML.
- Document trade-offs vs the brief's preference for YAML
- How JSON file would look for our schema

Recommend one. The brief leans YAML; if you find Path A cheaper than
expected (e.g. ≤200 LOC) confirm it. If Path A turns out costly (≥500
LOC for edge cases), switch recommendation to JSON — but explain why.

### 9. Resource URI scheme design

Per concept docs, resources have URIs like:
- `niagara://overview`
- `niagara://kinds/catalog`
- `niagara://equipment/{type}/{id}` — template
- `niagara://spaces/{path}`
- `niagara://history/{ord}?from={ts}&to={ts}`
- `niagara://standalone-points/{id}`

Decisions to make:
- Should `niagara://` be the scheme, or is there a reason to use
  `mcp://` or just `/`? MCP spec doesn't restrict.
- For templates with multiple params, how does the client know
  parameter shape? Spec says use RFC 6570 URI templates — confirm.
- For history with query parameters (`?from=&to=`), is that supported
  by spec for resource URIs, or do we use a different mechanism?

Read MCP spec 2025-06-18 sections on resource templates carefully and
report what's permitted.
