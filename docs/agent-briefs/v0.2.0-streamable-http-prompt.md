# niagaramcp v0.2.0: Streamable HTTP transport

## Mission

Add Streamable HTTP MCP transport (per spec 2025-06-18) alongside the
existing SSE+messages transport. Per recon
`docs/recon-2026-05-09.md` §13.11: zero blockers, three refactor-needed
items (session model, routing extension, doc drift), seven
clean-addition items.

The recon is your spec. Read it before every commit; don't deviate
from its file:line references without strong reason.

This is **focused implementation work with a smoke-test runbook**.
No new dependencies. Java 8 only (per §13.8). Backward compatibility
with `/sse` + `/messages` is mandatory.

## Hard constraints

- **Don't break the existing SSE+messages flow.** Every change must
  preserve `GET /sse` and `POST /messages?sessionId=…` behaviour.
- **Java 8 only.** No `var`, no records, no switch expressions, no
  text blocks, no `Map.of`/`List.of`. Lambdas, streams, method
  references, `CompletableFuture` are fine.
- **No new runtime dependencies.** Only what's already on classpath
  (`baja`, `control-rt`, `web-rt`, `nre`, javax.servlet 3.1
  compileOnly, embedded `com.niagaramcp.json`).
- **No new threads.** Per recon §10.4 the module has zero
  `ExecutorService`/`Thread.start()`. Keep it that way. Lazy idle
  eviction = check on acquire, no scheduler.
- **All new code under `com.niagaramcp.server`** package. Don't
  touch `com.niagaramcp.json`.
- **Don't rewrite tools.** They're protocol-agnostic (recon §8); the
  five existing tools work unchanged.
- **No edits to `_CODE_REVIEW.md`** (historical doc).
- **Atomic commits.** Each commit must compile (if you can build)
  and leave the SSE flow working.
- **Don't merge to main.** Leave the branch unmerged for human
  review.

## The seven commits

### Commit 1 — `docs(adr): 0001 Streamable HTTP transport design`

Create `docs/adr/0001-streamable-http-transport.md` (create the
`docs/adr/` directory). The ADR formalises decisions from recon §13
before any code changes.

Sections:
- **Status**: PROPOSED — 2026-05-09
- **Context**: 2-3 paragraphs summarising why we add this transport
  (deprecation of SSE in MCP spec, n8n-class clients increasingly
  default to Streamable HTTP, internal use case per Mikhail's brief).
  Reference recon §13 conclusions.
- **Decision**: Five sub-decisions, each with one paragraph:
  1. Add Streamable HTTP **alongside** SSE — both transports
     coexist on the same servlet at different paths
     (recon §13.3, §13.6).
  2. Extract `Session` interface; `McpSession` becomes
     `SseSession implements Session`; new
     `StreamableSession implements Session` (recon §13.2).
  3. Session lifecycle uses **lazy idle eviction** — no scheduler
     threads, no background tasks. Each acquire checks
     `(now - lastSeenMs) > IDLE_TIMEOUT_MS`; stale sessions are
     removed at that point (recon §10.4 — preserves the
     "no new threads" baseline).
  4. Default `IDLE_TIMEOUT_MS = 30 minutes`. Configurable via
     `BMcpPlatformService` property (analogous to existing
     `sseHeartbeatSec`).
  5. Bump MCP `PROTOCOL_VERSION` to `"2025-06-18"` (recon §5.3).
- **Consequences**:
  - Positive: clean addition; backward compat preserved; no thread
    pool added; tools unchanged.
  - Negative: code surface grows ~250 LOC; `Mcp-Session-Id` and
    `sessionId` (legacy query param) coexist as two session ID
    namespaces — minor cognitive overhead.
- **Alternatives considered**:
  - *Replace SSE entirely*: rejected, breaks existing deployments.
  - *Scheduled cleanup with `ScheduledExecutorService`*: rejected,
    introduces first thread in the codebase, more lifecycle
    complexity. Lazy eviction is sufficient for current scale.
  - *Separate servlet `McpStreamableServlet`*: rejected, duplicates
    auth/enabled checks for marginal isolation.
- **Open items / follow-ups**:
  - Server-initiated messages (`GET /mcp` for SSE-style push to
    client) — implemented but not exercised by any current tool.
  - OAuth2 resource server profile (Bearer JWT validation) —
    deferred to v0.3.0 or later.

Length: 1-2 pages. Reference specific file:line from recon, e.g.
`McpSession.java:11-67`, `McpServlet.java:41-62`. Concrete > abstract.

Commit message:
```
docs(adr): 0001 Streamable HTTP transport design

Formalise the design decisions from docs/recon-2026-05-09.md §13
before implementation. Five decisions: coexist with /sse, extract
Session interface, lazy idle eviction, 30-minute default timeout,
protocol version 2025-06-18.

Refs: docs/recon-2026-05-09.md §13.1-13.10
```

Files:
- New: `niagaramcp-rt/src/com/niagaramcp/server/Session.java`

`Session.java` interface:

```java
public interface Session {
  String getSessionId();
  boolean isInitialized();
  void markInitialized();
  boolean isClosed();
  void close();
  /** Update the lastSeenMs marker for idle eviction. No-op for SSE. */

```

`SseSession.java` (renamed from `McpSession.java`): keep all current
behaviour (the `LinkedBlockingQueue`, `enqueue`, `poll`, `__CLOSE__`
sentinel, MAX_QUEUE=1000, all of it). Add `implements Session`.
`touch()` is a no-op for SSE — its lifecycle is bound to the GET
connection per recon §6.5, idle timeout doesn't apply.

`McpSessions.java`: change the registry value type from `McpSession`
(now `SseSession`) to `Session`. The `create()` helper that builds
SSE sessions now becomes `createSse()` returning `SseSession`. Add
`get(sessionId)` returning `Session`. Existing
`closeAll()` / `remove()` / `activeCount()` work on the interface.

`McpServlet.java`: update `handleSse` to call `createSse()`; update
`handleMessage` to cast `Session` to `SseSession` for the queue
enqueue (or expose enqueue via Session interface — see below). The
cast approach is fine for now: the message-path is SSE-specific by
construction.

Decision on enqueue: **don't add `enqueue` to the `Session`
interface**. Streamable HTTP doesn't enqueue the same way (replies
are written to the response stream of the same POST). Keep `enqueue`
as `SseSession`-specific. The cast `(SseSession) session` lives only
in `handleMessage`.

`McpProtocol.handle(JSONObject, ToolRegistry, Session)` — change the
parameter type from `McpSession` (now nonexistent) to `Session`. The
body uses only `session.markInitialized()` (recon §5.2 line 53-54),
which is on the interface.

`BMcpPlatformService.java`: no changes needed — it doesn't reference
`McpSession` directly per recon §3.

After this commit: SSE flow works exactly as before, and the
codebase has a clean abstraction point for Streamable HTTP to plug
in.

### Commit 3 — `feat: add StreamableSession with lazy idle eviction`

Files:
- New: `niagaramcp-rt/src/com/niagaramcp/server/StreamableSession.java`
- Edited: `McpSessions.java`, `BMcpPlatformService.java`

`StreamableSession.java`:

```java
public final class StreamableSession implements Session {
  public static final long DEFAULT_IDLE_TIMEOUT_MS = 30 * 60 * 1000L;

  private final String sessionId;
  private volatile long lastSeenMs;
  private volatile boolean initialized;
  private volatile boolean closed;

  StreamableSession(String sessionId) {
    this.sessionId = sessionId;
    this.lastSeenMs = System.currentTimeMillis();
  }

  public String getSessionId() { return sessionId; }
  public boolean isInitialized() { return initialized; }
  public void markInitialized() { this.initialized = true; }
  public boolean isClosed() { return closed; }
  public void close() { this.closed = true; }
  public void touch() { this.lastSeenMs = System.currentTimeMillis(); }
  public long getLastSeenMs() { return lastSeenMs; }

  public boolean isStale(long idleTimeoutMs) {
    return (System.currentTimeMillis() - lastSeenMs) > idleTimeoutMs;
  }
}
```

No queue. No `__CLOSE__` sentinel. Pure state-only object. The
servlet writes responses directly to the POST's HTTP response.

`McpSessions.java` additions:
- `createStreamable()` — generates UUID, allocates
  `StreamableSession`, puts into the registry, returns it.
- `acquireStreamable(String sessionId, long idleTimeoutMs)` — looks
  up by id; if not found returns null; if found and stale, removes
  and returns null; if found and fresh, calls `touch()` and returns
  the session.

```java
public static StreamableSession acquireStreamable(String sessionId, long idleTimeoutMs) {
  Session s = SESSIONS.get(sessionId);
  if (!(s instanceof StreamableSession)) return null;
  StreamableSession ss = (StreamableSession) s;
  if (ss.isClosed() || ss.isStale(idleTimeoutMs)) {
    SESSIONS.remove(sessionId);
    ss.close();
    return null;
  }
  ss.touch();
  return ss;
}
```

`BMcpPlatformService.java`: add a new property
`mcpSessionIdleTimeoutSec` (default 1800 = 30 minutes), with
`@NiagaraProperty` annotation following the pattern of existing
`sseHeartbeatSec`. Add a static accessor
`mcpSessionIdleTimeoutMs()` that returns the value × 1000.

After this commit: `StreamableSession` exists in the codebase but
no servlet path constructs or uses it yet. Build still passes.

If you can build: `./gradlew niagaramcp-rt:assemble` must succeed.

### Commit 5 — `feat: implement Streamable HTTP request/response handling`

Files: `McpServlet.java` (the three handlers).

`handleStreamablePost`:
1. Read `Mcp-Session-Id` header. If absent → check if request is
   `initialize` (parse body first):
   - If yes: generate new UUID, create `StreamableSession`, set
     `Mcp-Session-Id` response header to the new id.
   - If no: respond `400 Bad Request` ("missing Mcp-Session-Id;
     send `initialize` first").
2. If header present: `acquireStreamable(id, idleTimeoutMs)`. If
   null → `404 Session not found or expired`.
3. Parse JSON-RPC body (reuse `readJson(req)`).
4. Call `McpProtocol.handle(request, registry, session)`.
5. If response is null (notification) → `202 Accepted`, empty body.
6. Else → `200 OK`, `Content-Type: application/json`, body =
   `response.toString()`.

For now, **don't implement streaming response shape**
(`text/event-stream` reply on POST). Always return unary
`application/json`. This is spec-compliant — streaming is optional
on POST. We may add it later if a tool produces progress
notifications mid-call.

`handleStreamableGet`:
1. Read `Mcp-Session-Id` header. Required.
2. `acquireStreamable(...)`. If null → 404.
3. Open `text/event-stream` response (same headers as
   `handleSse` per `McpServlet.java:65-69`).
4. Park: there's no per-session queue for Streamable sessions.
   Without server-initiated messages, the simplest implementation
   is to respond with a `Content-Type: text/event-stream` and a
   single `: stream-open\n\n` comment, then return immediately
   (closes the response).

   This is a degenerate implementation but spec-allowed: the spec
   permits the server to immediately end an SSE response if it has
   nothing to push. A future iteration can add a real push channel.

   **Document this in the handler with a comment explaining why.**

`handleStreamableDelete`:
1. Read `Mcp-Session-Id` header. Required.
2. `McpSessions.remove(sessionId)` — atomic remove + close.
3. `204 No Content`.

If you can build: `./gradlew niagaramcp-rt:assemble` must succeed.

Commit message:
```
feat: implement Streamable HTTP request/response handling

- on `initialize` without Mcp-Session-Id, generate one and
  return in response header
- otherwise validate header, dispatch via McpProtocol.handle(),

Real server-initiated push deferred to a future iteration; current
tools don't produce mid-call progress.

```
