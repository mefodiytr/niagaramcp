## Surprises / things imprecise

### What went exactly as brief predicted

- All 4 diagnostic tools fit comfortably within the ~150 LOC budget
  (actual: 360 LOC across 4 files, but ~75 LOC per file is
  Apache header + javadoc, code per file is ~50 LOC — within
  estimate).
- `/health` endpoint: ~70 LOC (brief estimated ~40), slightly over
  due to JSON shape building + JavaDoc justification of the
  no-auth exception.
- 3 properties + JSON-RPC error standardisation: ~145 LOC (brief
  estimated 80), over because adding 8 error-code constants with
  per-code JavaDoc + `error.data` plumbing through `RpcException`
  added more boilerplate than expected.
- Smoke client: ~147 LOC (brief estimated 80), over because each
  step needs urllib boilerplate for the no-auth `/health` call
  plus Python error handling.

### Recon errors caught at compile (none significant)

- `BAlarmService` is in `javax.baja.alarm` package, accessible via
  `:alarm-rt` already in gradle from v0.3.0 — no surprise.
- `BHistoryService.TYPE` access works via `Sys.getService()` —
  pattern from v0.3.0 ReadHistoryTool reused.
- `GetServerInfoTool.NIAGARAMCP_VERSION` initially package-private
  static, but `McpServlet` (different package) needs to read it
  from `handleHealth`. Promoted to `public` in commit 3.

### Brief vs actual divergences

- Brief: "wire mcpProtocolVersion accessor to `McpProtocol.SERVER_VERSION`
  constant". Actual: wired to `PROTOCOL_VERSION` (which is the MCP
  protocol version), NOT `SERVER_VERSION` (which is the server
  product version, "1.0.0"). The brief instruction appears to
  conflate the two — semantic intent of `mcpProtocolVersion` clearly
  matches `PROTOCOL_VERSION`. Documented in commit 4 message and
  here.
- Brief: "Existing 401/404 HTTP responses unchanged — these are
  JSON-RPC-level errors at HTTP 200 with error body". Reading this
  carefully: the new `-32001..-32008` codes apply at the JSON-RPC
  level. HTTP 401/404 (auth failure / wrong session ID) stay at
  HTTP layer. All good — no conflict.
- Brief mentioned 15 existing smoke client steps. Actual: 13
  numbered steps existed in v0.3.0 (1-13). Adding 5 → 14-19, total
  19 numbered steps. Close enough; banner now says 19.

### Things I noticed but didn't change

- `tools/list` count is now 32, but in code there's no central
  source of truth for the "expected count" — smoke client step 1
  in `run_streamable_tests` does verify "tools/list returns ≥
  some baseline" but doesn't exact-match. Acceptable because
  `disabledTools` can legitimately reduce the count.
- `getServerInfo` reports `transports: ["sse", "streamable-http"]`
  hardcoded. If a future version adds a third transport we have
  to update both the registration and this list. Cleanest fix
  later: query a transport registry. Not worth doing now.
- `probeOrd` uses `BControlPoint`, `BIWritablePoint`, `BHistoryExt`,
  `BAlarmSource` import scope. All compile under existing gradle
  deps (alarm-rt + control-rt + history-rt — all from v0.3.0).
