## `linkSlots` `converterType` arg (commit `67de7a0`)

Optional `"module:Type"` arg. When present:

1. `Sys.getType(converterType).getInstance()` → must be a
   `javax.baja.util.BConverter` (else `-32602`; if the type doesn't load,
   `-32005`).
2. `sink.checkLink(source, sourceSlot, sinkSlot, null)` still runs, but
   an `isValid()==false` result no longer raises `-32016` — the caller is
   explicitly bridging the mismatch. The invalid reason is recorded in the
   result as `linkCheckNote`. (Without a `converterType`, behaviour is
   unchanged: invalid → `-32016 ERR_LINK_TYPE_MISMATCH`.)
3. Inside the gateway: `BLink link = new BConversionLink(source,
   sourceSlot, sinkSlot, converter)` (vs. `sink.makeLink(...)` for the
   plain case), then `sink.add(linkName, link, cx)`.

Result envelope gains `linkType` (`"link"`/`"conversionLink"`), and —
when a converter was used — `converter` (the type spec) and, if
`checkLink` was bypassed, `linkCheckNote`.

An incompatible named converter isn't caught up front (there's no public
"can this converter bridge A→B" predicate) — the link is added but faults
at runtime (inspect the link slot), or `add()`/activation rejects it →
`-32603` with Niagara's message. Documented in the tool's javadoc and
description.

No `convert: true` auto-pick — per design Q6 (made back in v0.5.1): the
converter must be named explicitly, both to avoid surprise conversions and
because there is no stable public converter registry to walk (Workbench
uses the agent registry for its converter picker).

## Recon notes (baja 4.15.3.28)

- `javax.baja.sys.BConversionLink extends BLink` — ctor
  `(BComponent source, Slot sourceSlot, Slot sinkSlot, BConverter
  converter)`; `getConverter()` / `setConverter()`. No
  `makeConversionLink()` on `BComponent` — use the ctor + `sink.add(...)`.
- `javax.baja.util.BConverter` — `abstract extends BStruct`;
  `convert(BObject, BObject, Context)`. Concrete: `baja:NullConverter`
  (no-op) and module-specific subclasses.
- `javax.baja.sys.LinkCheck` — `final`; only `isValid()` /
  `getInvalidReason()`. No `isValidWithConversion()` and it doesn't
  enumerate available conversions — hence the bypass-on-`converterType`
  approach.
- No public converter registry for a type pair (Workbench uses agent
  registry / `BTypeSpec` agents) — so explicit `converterType` it is.
