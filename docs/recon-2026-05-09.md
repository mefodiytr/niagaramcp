## §4 — Servlet registration & URL routing

### 4.1 Which class is the servlet

`McpServlet` (`McpServlet.java:36`):

```java
public final class McpServlet extends UnauthenticatedServlet {
```

Parent class is `javax.baja.web.servlets.UnauthenticatedServlet` (import at `McpServlet.java:22`), which itself extends `javax.servlet.http.HttpServlet` (verified during the original build session — see `_SMOKE_TEST.md` mention of `web-rt.jar`). The `Unauthenticated` part means **the Niagara web container will call this servlet WITHOUT first checking Niagara user/session credentials**. This is exactly why the `UNAUTHENTICATED_ACCESS` permission is requested in `module-permissions.xml:15-18`.

### 4.2 URL pattern declaration

The URL pattern is **declared in `WEB-INF/web.xml`** (`niagaramcp-rt/src/WEB-INF/web.xml:4-11`):

```xml
<servlet>
  <servlet-name>McpServlet</servlet-name>
  <servlet-class>com.niagaramcp.server.McpServlet</servlet-class>
</servlet>
<servlet-mapping>
  <servlet-name>McpServlet</servlet-name>
  <url-pattern>/*</url-pattern>
</servlet-mapping>
```

The declaration uses standard Servlet 3.x web.xml — not a `@WebServlet` annotation, not `getDefaultDirectoryName()` override, not a Niagara `@NiagaraType` annotation. The **module name** (`niagaramcp` from `niagara-module.xml:2`) becomes the URL prefix, so the full address is:

```
https://<station-host>/niagaramcp/*
```

Inside the servlet, `req.getPathInfo()` returns the `/sse` or `/messages` portion; `stripSlash()` (`McpServlet.java:186-190`) trims the leading slash and the result is matched with `equals("sse")` or `equals("messages")` (`McpServlet.java:45`, `:57`).

### 4.3 Internal path → handler mapping

`doGet` (`McpServlet.java:41-50`):

```java
@Override
protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
  if (!checkServiceEnabled(resp)) return;
  if (!checkAuth(req, resp)) return;
  String path = stripSlash(req.getPathInfo());
  if ("sse".equals(path)) {
    handleSse(req, resp);
  } else {
    sendPlain(resp, 404, "Not Found: /" + path);
  }
}
```

`doPost` (`McpServlet.java:52-62`):

```java
@Override
protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws IOException {
  if (!checkServiceEnabled(resp)) return;
  if (!checkAuth(req, resp)) return;
  String path = stripSlash(req.getPathInfo());
  if ("messages".equals(path)) {
    handleMessage(req, resp);
  } else {
    sendPlain(resp, 404, "Not Found: /" + path);
  }
}
```

So the routing table is:

| Method | Path (relative to `/niagaramcp`) | Handler |
|---|---|---|
| GET  | `/sse`        | `handleSse(req, resp)` (`McpServlet.java:64`) |
| GET  | anything else | `sendPlain(resp, 404, ...)` |
| POST | `/messages`   | `handleMessage(req, resp)` (`McpServlet.java:113`) |
| POST | anything else | `sendPlain(resp, 404, ...)` |

### 4.4 Single servlet — both transports

There is **one servlet class** (`McpServlet`) handling both flavours — SSE (long-poll GET) and JSON-RPC inbound (short POST) — because both branches share `checkServiceEnabled`/`checkAuth` and share the `McpSessions` registry. The two branches diverge only after auth.

For Streamable HTTP, see §13.3: this single-servlet pattern can absorb the new `/mcp` path with a small if-else, OR a sibling servlet can be added. Both are viable.

### 4.5 Module name / URL relationship

The URL prefix `/niagaramcp/...` is determined by `moduleName="niagaramcp"` in `niagara-module.xml:2`. The Niagara web container mounts each module's web.xml under `/<moduleName>/`. There is no `getServletName()` override; the `<servlet-name>McpServlet</servlet-name>` in `web.xml:5` is purely an internal label tying the servlet declaration to its mapping.

This is convenient: if we ever rename the module, the URL changes automatically. It's also the only place where the public URL is determined — there's no second mention of `/niagaramcp/` in any code path.

## §5 — MCP protocol dispatcher

### 5.1 Single-method API

`McpProtocol.handle()` (`McpProtocol.java:39`):

```java
public static JSONObject handle(JSONObject request, ToolRegistry registry, McpSession session) {
```

This is the only public entry point of the protocol layer. It takes a parsed JSON-RPC request, the active tool registry (from `BMcpPlatformService.getRegistry()`), and an `McpSession` (currently always non-null when called from `handleMessage`, because `handleMessage` rejects unknown sessionIds at `McpServlet.java:120-123` before dispatching).

Returns a `JSONObject` to send back, or `null` if the request was a notification (no `id`).

### 5.5 Error handling

Three categories:

1. **`RpcException`** (`McpProtocol.java:165-173`) — internal class for tool-dispatch errors with explicit JSON-RPC error codes. Caught at `McpProtocol.java:71-72` and turned into a JSON-RPC error response.
2. **Other `Exception`** — caught at `McpProtocol.java:73-75`, returned as `ERR_INTERNAL` (-32603) with the exception message.
3. **Tool-call exceptions** — caught inside `callTool()` (`McpProtocol.java:125-130`). The tool's exception becomes `text = "Error: " + e.getMessage()` and `isError = true` in the content array. The JSON-RPC envelope itself remains successful (`ok` reply).

So at JSON-RPC level there are three response shapes: success (`{result: ...}`), error (`{error: {code, message}}`), or null (notification). At the MCP-content level, tool-call errors become *content entries* with `isError: true`, not RPC-level errors. This is consistent with the MCP spec.

## §6 — SSE transport specifics

This is the section most directly relevant to the Streamable HTTP work — it documents what's coupled to SSE today.

### 6.1 SSE response opening

`handleSse()` (`McpServlet.java:64-111`) opens the stream with these headers (`McpServlet.java:65-69`):

```java
resp.setStatus(200);
resp.setContentType("text/event-stream; charset=utf-8");
resp.setHeader("Cache-Control", "no-cache");
resp.setHeader("Connection", "keep-alive");
resp.setHeader("X-Accel-Buffering", "no");
```

Then it creates a fresh session, sends an `event: endpoint` SSE event whose `data:` payload is the absolute path `<contextPath>/messages?sessionId=<UUID>`, flushes once, and enters the loop.

### 6.2 Session creation and lookup

`McpSession session = McpSessions.create();` at `McpServlet.java:71`.

`McpSessions.create()` (`McpSessions.java:30-35`) generates a UUID-v4 via `UUID.randomUUID().toString()`, allocates a new `McpSession`, and inserts into the static `ConcurrentHashMap` (`McpSessions.java:28`).

Inbound POSTs reach the session via `McpSessions.get(sessionId)` (`McpSessions.java:37-39`) at `McpServlet.java:119`:

```java
McpSession session = McpSessions.get(sessionId);
if (session == null) {
  sendPlain(resp, 404, "Unknown sessionId");
  return;
}
```

So the session model is: **one SSE GET = one session = one UUID**. The session is created *by the SSE GET handler*, and POSTs must come back with the right sessionId in the query string. If the SSE connection drops and the client doesn't open a new one, the session also gets removed (see §6.5) and subsequent POSTs hit the 404 branch.

### 6.3 Inbound POST → outbound SSE plumbing

`handleMessage()` (`McpServlet.java:113-141`):

```java
String sessionId = req.getParameter("sessionId");
...
JSONObject session = McpSessions.get(sessionId);
...
JSONObject request = readJson(req);   // reads request body
JSONObject response = McpProtocol.handle(request, BMcpPlatformService.getRegistry(), session);
if (response != null) {
  session.enqueue(response.toString());
}
resp.setStatus(202);
```

So a POST *receives* a request, dispatches it synchronously through `McpProtocol.handle()`, then enqueues the response onto the **per-session outbound queue** (`McpSession.outgoing` BlockingQueue). The HTTP response is `202 Accepted` — the actual reply is delivered asynchronously, on the SSE channel of the same session.

### 6.4 SSE flush loop and keep-alive

`handleSse()` loop (`McpServlet.java:83-106`):

```java
while (!session.isClosed()) {
  String msg;
  try {
    msg = session.poll(heartbeatMs);
  } catch (InterruptedException ie) {
    Thread.currentThread().interrupt();
    break;
  }
  if (msg == null) {
    w.write(": ping\n\n");
    w.flush();
  } else {
    if ("__CLOSE__".equals(msg)) {
      break;
    }
    w.write("event: message\n");
    w.write("data: " + msg + "\n\n");
    w.flush();
  }

  if (w.checkError()) {
    break;
  }
}
```

`session.poll(timeoutMs)` (`McpSession.java:73-75`) is `outgoing.poll(timeoutMs, MILLISECONDS)`. When timeout elapses without a message, the loop sends an SSE comment (`: ping\n\n`) — these are valid SSE no-ops to keep proxies/load balancers from closing the connection.

`heartbeatMs` is read once at loop entry from `BMcpPlatformService.sseHeartbeatSec()` (`McpServlet.java:81`, default 25 s, configurable via property), then `* 1000L`. A `Math.max(1, ...)` guard prevents zero/negative heartbeat intervals.

The sentinel `"__CLOSE__"` is used by `McpSession.close()` (`McpSession.java:77-82`) to wake a polling reader and let it exit cleanly. The literal is duplicated in `McpServlet.java:95` (`"__CLOSE__".equals(msg)`) and `McpSession.SENTINEL_CLOSE` (`McpSession.java:30`) — `_CODE_REVIEW.md:120` already flags this as a unify-the-constant nit.

`w.checkError()` (`McpServlet.java:103`) detects a TCP-level write error from a prior flush; when true, the loop exits.

### 6.5 Session cleanup

`finally` block (`McpServlet.java:107-110`):

```java
} finally {
  McpSessions.remove(session.getSessionId());
  bcLog("SSE close sid=" + session.getSessionId());
}
```

`McpSessions.remove()` (`McpSessions.java:41-46`) atomically removes from the static map AND calls `session.close()`, which sets `closed=true` and offers `__CLOSE__` to the queue. So even if the session has been removed by `closeAll()` first (e.g. on `serviceStopped`), the cleanup is idempotent.

Combined: **session lifetime is bound to one SSE connection**. There is no concept of "reconnect to the same session" — Streamable HTTP, with its `Mcp-Session-Id` header allowing reconnection and multi-connection sessions, will need a new lifecycle (see §13.2).

### 6.6 Concurrent connections

Tracked entirely in the static map `McpSessions.SESSIONS` (`McpSessions.java:28`). Each entry is one open SSE connection (one Niagara worker thread blocked in `handleSse`). `activeCount()` (`McpSessions.java:55-57`) returns `SESSIONS.size()`. There is no cap, no limit-and-evict policy.

A high concurrent-connection count means a high count of blocked HTTP worker threads — this is the most expensive resource of the design. On Jetty 9.4 the worker pool defaults to 200 threads, so the practical cap is in the low hundreds. Above that, new SSE GETs would queue.

### 6.7 Threading

- **SSE flush loop**: runs *on the Niagara HTTP worker thread* that accepted the GET. The thread spends most of its time `BlockingQueue.poll()`-ing — i.e. parked. No dedicated executor.
- **POST handler**: runs *on the Niagara HTTP worker thread* that accepted the POST. `McpProtocol.handle()` is called synchronously; tool dispatch is synchronous. For a slow tool (e.g. BQL on a big history) this thread blocks for the duration of the tool call.
- **No `ExecutorService`, `ScheduledExecutorService`, or `Thread.start()`** anywhere in our code — verified by grep. Niagara's web container provides the only thread pool used.

This is fine for SSE (the pool is sized for blocking HTTP) but worth noting for §13.5: Streamable HTTP doesn't change the threading model materially — POSTs stay synchronous and either return immediately or stream chunked, both of which fit the same blocking-thread model.

### 6.8 Backpressure

`McpSession.enqueue()` (`McpSession.java:58-67`):

```java
public void enqueue(String jsonRpcMessage) {
  if (closed) return;
  if (!outgoing.offer(jsonRpcMessage)) {
    BMcpPlatformService instance = BMcpPlatformService.instance();
    if (instance != null) {
      instance.bcLog("SSE queue overflow (>" + MAX_QUEUE + ") sid=" + sessionId
          + " — dropping message; client likely slow or stuck");
    }
  }
}
```

The queue is bounded to `MAX_QUEUE = 1000` (`McpSession.java:31`). When full, **the message is dropped silently with a warning logged** — the producer (POST handler) doesn't block. This was added before v0.1.0 (CHANGELOG `niagaramcp/CHANGELOG.md:59-62`) explicitly to prevent unbounded heap growth from a slow client.

For Streamable HTTP this matters because the session-level outbound queue is currently shared with SSE semantics. Whether Streamable HTTP keeps the same queue or maintains its own response-per-request model is the key design question (see §13.2).

## §7 — Bearer authentication

### 7.1 Header parsing

`McpServlet.checkAuth()` (`McpServlet.java:151-168`):

```java
private static boolean checkAuth(HttpServletRequest req, HttpServletResponse resp) throws IOException {
  String expected = BMcpPlatformService.apiToken();
  if (expected == null || expected.length() == 0) {
    sendUnauthorized(resp, "MCP apiToken is not configured on the service");
    return false;
  }
  String header = req.getHeader("Authorization");
  if (header == null || !header.startsWith("Bearer ")) {
    sendUnauthorized(resp, "Missing Bearer token");
    return false;
  }
  String token = header.substring(7).trim();
  if (!expected.equals(token)) {
    sendUnauthorized(resp, "Invalid token");
    return false;
  }
  return true;
}
```

The header is parsed at `McpServlet.java:157` via `req.getHeader("Authorization")`, prefix-stripped at `:162`. **Comparison is `String.equals`** — not constant-time. For UUID-length tokens this leaks at most ~1 byte/timing-leak, which is academic; for shorter tokens (which the schema doesn't forbid), it's a measurable side channel. `_CODE_REVIEW.md:158` already noted this.

### 7.2 Token storage

The token lives as a Niagara `String` property on `BMcpPlatformService` (`BMcpPlatformService.java:65-67`):

```java
public static final Property apiToken = newProperty(0, "", null);
public String getApiToken() { return getString(apiToken); }
public void setApiToken(String v) { setString(apiToken, v, null); }
```

Default value is `""`. The static accessor `BMcpPlatformService.apiToken()` (`BMcpPlatformService.java:151-154`) returns the running instance's token (or `""` if no instance is running):

```java
public static String apiToken() {
  BMcpPlatformService s = INSTANCE;
  return (s == null) ? "" : s.getApiToken();
}
```

`INSTANCE` (`BMcpPlatformService.java:85`) is a `static volatile` field set on `serviceStarted()` (`:108`) and cleared on `serviceStopped()` (`:119`).

Storage location: in the station's `.bog` config file as a plain unencrypted string. Visible to any Workbench user with view access to the service (`_CODE_REVIEW.md:67`).

### 7.3 Auth failure

`sendUnauthorized()` (`McpServlet.java:170-173`):

```java
private static void sendUnauthorized(HttpServletResponse resp, String body) throws IOException {
  resp.setHeader("WWW-Authenticate", "Bearer");
  sendPlain(resp, 401, body);
}
```

`sendPlain` writes status 401 + a `text/plain` body explaining the failure mode (`No apiToken configured` / `Missing Bearer token` / `Invalid token`). Connection is **not** dropped; the response completes normally and the client may retry.

Note: the body is informative — it tells an attacker **whether the token is missing vs invalid**. That's a minor info leak, not exploitable when tokens are random UUIDs but worth noting.

### 7.4 Auth coverage

`checkAuth` is called at the top of **both** `doGet` (`McpServlet.java:43`) and `doPost` (`McpServlet.java:55`), before any path matching. So:

- `GET /sse` → `checkServiceEnabled` → `checkAuth` → handler.
- `POST /messages` → `checkServiceEnabled` → `checkAuth` → handler.
- Any other path or method → 404 *after* `checkServiceEnabled`+`checkAuth`. (Well — `doPut`, `doDelete`, etc., are inherited from `HttpServlet` defaults and respond with 405; they don't go through `checkAuth`. Probably fine, but worth a note.)

`initialize` is **not** treated specially. The `Authorization` header must be present on the very first SSE GET — there is no MCP-spec exception for the handshake. This is fine for the SSE flow; for Streamable HTTP, the spec allows server-driven `WWW-Authenticate` challenges with OAuth — see §13.4.

## §9 — Embedded JSON library

### 9.1 Public API surface

The library is the standard `org.json` (stleary) family, repackaged into `com.niagaramcp.json`. Two main entry points used by our code:

```java
// JSONObject.java:49
public JSONObject(JSONTokener x) throws JSONException { ... }
```

(consumer: `McpProtocol.buildToolsList` at `McpProtocol.java:100`, `McpServlet.readJson` at `McpServlet.java:183`)

```java
// JSONTokener.java:39
public JSONTokener(String s) { ... }
```

(used to wrap request bodies before constructing `JSONObject`)

Other primary methods used:
- `JSONObject.put(String, Object)` — used everywhere for response building.
- `JSONObject.get/optString/optJSONObject/optString/getString/getInt/has/isNull` — used for argument extraction in tools.
- `JSONArray.put(Object)` — used in `McpProtocol.buildToolsList` and `ListChildrenTool.childrenJson`.
- `JSONObject.NULL` — used to mirror the `id` field even when the request was a notification (`McpProtocol.java:148`).

### 9.2 Streaming?

No — `JSONTokener` reads from a `Reader` or `String`, but `JSONObject(tokener)` materialises the entire object graph into memory before returning. There is no SAX-style or push parser.

For this module that's fine — JSON-RPC envelopes are small. For Streamable HTTP responses that might be large (tool results can be many KB of TSV), the same materialise-all approach applies — we'd build a `JSONObject`/`JSONArray` and call `toString()`.

### 9.3 Why embedded?

The README says the embedding is to avoid a dependency on the parent `niagaramcp-json` module (`README.md:218`). Looking at the project context (the original `platMcp` was deployed alongside an MCS station that already had this library available), the trade-off was:

- **Embed**: jar grows ~100 KB, but the module is self-contained and can deploy to any 4.15 station.
- **Depend on external module**: smaller jar, but requires installing both modules.

The decision was to embed. This matters for §13.7: **adding a new transport doesn't add JSON dependencies** — we use what's already in-tree. There's nothing to bring in.

There are no comments in the JSON sources explaining the embedding decision; only the README note. The build script's `compileOnly("javax.servlet:...")` (`niagaramcp-rt.gradle.kts:33`) shows the team understood when *not* to embed (servlet API ships with Niagara at runtime), so the JSON embedding is a deliberate choice rather than oversight.

```java
  r.register((Tool) new BqlQueryTool());
  REGISTRY = r;
  INSTANCE = this;

  setStatus(getEnabled() ? "running" : "disabled");
  serviceIsRunning = true;
}
```

Steps:
1. `started()` — `BComponent` superclass startup.
2. Build a fresh `ToolRegistry`, register all 5 tools.
3. Publish the registry and `this` to the `static volatile` fields used by other classes.
4. Set the `status` slot for Workbench visibility.

`serviceStopped()` (`BMcpPlatformService.java:114-122`):

```java
@Override
public void serviceStopped() throws Exception {
  bcLog("serviceStopped");
  McpSessions.closeAll();
  REGISTRY = null;
  INSTANCE = null;
  setStatus("stopped");
  serviceIsRunning = false;
}
```

Steps:
1. Close every active SSE session (`McpSessions.closeAll()` at `McpSessions.java:48-53` iterates and offers `__CLOSE__` to each queue, then `SESSIONS.clear()`).
2. Null the static handles.
3. Update status.

`changed(Property, Context)` (`BMcpPlatformService.java:124-134`):

```java
@Override
public void changed(Property p, Context cx) {
  super.changed(p, cx);
  if (p == enabled && serviceIsRunning) {
    boolean en = getEnabled();
    setStatus(en ? "running" : "disabled");
    if (!en) {
      McpSessions.closeAll();
    }
  }
}
```

Reacts only to the `enabled` property: flipping to `false` closes all open SSE sessions; flipping back to `true` doesn't reopen anything (clients must reconnect).

### 10.2 Servlet lifecycle

`McpServlet` is registered in `WEB-INF/web.xml`. The Niagara web container instantiates it lazily on first request and keeps the instance for the lifetime of the web app. There is no `init()` or `destroy()` override in our code — it relies on the default `HttpServlet` lifecycle.

The servlet is **decoupled from `BMcpPlatformService`**: even if the service is stopped, the servlet still runs and answers `503` (via `checkServiceEnabled` at `McpServlet.java:143-149` calling `BMcpPlatformService.isEnabled()`, which returns `false` if `INSTANCE == null` per `BMcpPlatformService.java:146-149`).

### 10.3 Logging

There is **no real logging framework** in use. The single logging mechanism is `bcLog(String)`:

`BMcpPlatformService.bcLog()` (`BMcpPlatformService.java:140-144`):

```java
public void bcLog(String str) {
  if (getShowLog()) {
    System.out.println("niagaramcp BMcpPlatformService " + str);
  }
}
```

`McpServlet.bcLog()` (`McpServlet.java:202-206`):

```java
private static void bcLog(String s) {
  if (BMcpPlatformService.showLog()) {
    System.out.println("niagaramcp McpServlet " + s);
  }
}
```

Both write to stdout, gated by the `showLog` boolean property. **Not** through `java.util.logging`, **not** through `BLog`, **not** through `org.slf4j`. In a Niagara station, stdout is captured to `console.log` but is **not** visible in the Workbench Spy → Log Setup view. `_CODE_REVIEW.md:96` flags this; CHANGELOG `niagaramcp/CHANGELOG.md:73-74` defers a fix to v0.2.

For Streamable HTTP, this means new code should make a deliberate choice: continue with `bcLog` for consistency, or introduce a real logger as part of v0.2 work. See §13.

### 10.4 Explicit threading

Greps for `ExecutorService`, `ScheduledExecutorService`, `new Thread(`, `Thread.start()`:

## §13 — Decision-relevant observations for Streamable HTTP design

This section answers the design question one observation at a time.

### 13.1 Is the JSON-RPC dispatcher coupled to SSE? **NO — Clean addition**

`McpProtocol.handle()` (`McpProtocol.java:39`):

```java
public static JSONObject handle(JSONObject request, ToolRegistry registry, McpSession session) {
```

The dispatcher takes a parsed `JSONObject`, returns a `JSONObject` (or `null`), and only touches `session` for one purpose: marking it as initialized in `notifications/initialized` (`McpProtocol.java:53-54`). It **does not** know about HTTP, SSE events, queues, or transport headers.

A Streamable HTTP handler can call `McpProtocol.handle(request, registry, session)` exactly the same way — the only question is **what `session` argument to pass** (see §13.2). For everything else, the dispatcher is reusable as-is.

**Rank: Clean addition** — no refactor needed for the protocol layer.

### 13.2 Session model — assumes 1 SSE connection per session. **Refactor needed**

Current model (`McpServlet.handleSse:71`, `McpSession.java:11-67`, `McpSessions.java:30-46`):

```
GET /sse → McpSessions.create() → new UUID + new McpSession with bounded queue
                                ↓
SSE GET thread parks on session.poll(heartbeatMs) and writes incoming queue items as SSE events
                                ↑
POST /messages?sessionId=… → McpSessions.get(sessionId) → session.enqueue(response.toString())
```

The session is created by the SSE GET, not by client choice. The client learns the sessionId from the first SSE `event: endpoint` payload (`McpServlet.java:76-78`). The session dies when the SSE GET returns (`McpServlet.java:107-110`).

**Streamable HTTP needs different semantics** (per MCP spec 2025-06-18):
- Server may issue or accept an `Mcp-Session-Id` header.
- One session can span multiple HTTP requests/responses.
- A single POST returns either a unary `application/json` reply OR a streamed `text/event-stream` reply.
- Sessions can be explicitly closed by the client (`DELETE`).
- Reconnect: client may resume a previous session by replaying its `Mcp-Session-Id`.

What needs extracting/adding:
- A **session model** with `Mcp-Session-Id` semantics, distinct from the current "session=SSE-connection" coupling.
- The current `McpSession` could be the basis: rename the queue-and-close fields into a transport-agnostic Session interface, and have **`SseSession extends Session`** (with the queue) and **`StreamableSession extends Session`** (with whatever lifecycle Streamable HTTP needs, e.g. last-seen timestamp + idle eviction).
- `McpSessions` becomes a registry of generic `Session`, keyed by `Mcp-Session-Id` (or UUID for SSE).

**Rank: Refactor needed** — non-trivial but contained. Suggested first step: introduce a `Session` interface; make `McpSession implements Session`; update `McpProtocol.handle(..., Session session)` signature; ensure SSE callsites still compile. Then add `StreamableSession` and a second factory.

### 13.3 Servlet registration — can one servlet handle both? **Refactor needed (small)**

Current routing (`McpServlet.doGet/doPost` at `McpServlet.java:41-62`):

```java
String path = stripSlash(req.getPathInfo());
if ("sse".equals(path)) handleSse(...);    // only in doGet
if ("messages".equals(path)) handleMessage(...);  // only in doPost
```

Adding Streamable HTTP would extend the routing table to:

```java
// doGet
if ("sse".equals(path)) handleSse(...);                  // legacy SSE GET
if ("mcp".equals(path)) handleStreamableGet(...);        // NEW: optional spec path

// doPost
if ("messages".equals(path)) handleMessage(...);         // legacy SSE-companion POST
if ("mcp".equals(path)) handleStreamablePost(...);       // NEW: unified endpoint

// doDelete (NEW)
if ("mcp".equals(path)) handleStreamableDelete(...);     // session close
```

The single-servlet pattern absorbs this comfortably — `McpServlet` already has `checkServiceEnabled`+`checkAuth` shared up top. Adding two-three new branches is mechanical.

**Alternative**: a second servlet class (`McpStreamableServlet`) registered at a different `<servlet-mapping>` in `web.xml`. This isolates concerns more cleanly but duplicates the auth/enabled checks. Probably not worth it for two endpoints — keep the single-servlet design and refactor `checkAuth` into something callable from either branch (it already is, since it's a static private method).

**Rank: Refactor needed (small)** — extend the routing table inside `McpServlet`, no new servlet class needed.

### 13.4 Auth layer placement — auth is above transport. **Clean addition**

`checkAuth(req, resp)` is called *before* path matching at `McpServlet.java:43` and `:55`. This means **adding a new path doesn't have to re-implement auth**: it inherits the existing bearer check for free.

Streamable HTTP gets:
- The same `Authorization: Bearer <apiToken>` requirement.
- The same `WWW-Authenticate: Bearer` 401 challenge on missing/wrong token.
- The same fail-secure behaviour when `apiToken` is empty.

This is one of the strongest pieces of the existing design — auth is genuinely transport-agnostic.

**Rank: Clean addition** — no auth code changes needed for the new transport.

(Caveat: if the new transport wants to support the spec's optional OAuth resource-server profile with `WWW-Authenticate: Bearer realm=...`, that's a *separate* extension — but it's orthogonal to the SSE-vs-Streamable question.)

### 13.5 Tool dispatch threading model — fits both transports. **Clean addition**

Current model (§6.7): tools are called synchronously on the HTTP worker thread that received the POST. The POST returns `202` after enqueuing the response; the SSE thread later writes the response.

Streamable HTTP changes the *response shape* but not the *call shape*:

- **Unary mode**: POST → call tool synchronously → return `application/json` reply with the result. Same call, different response writing.
- **Streaming mode**: POST → call tool synchronously → write `text/event-stream` to the response, with possibly multiple events (e.g. tool progress notifications + final result). Same call, transport writes happen in the POST's own thread instead of being enqueued elsewhere.

In both cases, the tool itself is called on the request thread, blocking until completion. That's exactly what happens now. The dispatcher needs no change.

If we ever want to support **server-initiated requests** to the client (which the MCP spec allows for some prompts), we'd need the server to push messages to the client — and Streamable HTTP supports that via the GET `text/event-stream` channel (similar to current SSE). That's where the queue model resurfaces; see §13.2.

**Rank: Clean addition** — the existing tool-call model fits.

### 13.6 Backward compat — `/sse` keeps working. **Clean addition**

`/sse` and `/mcp` would coexist on the same servlet, sharing:
- `checkServiceEnabled` (`McpServlet.java:143`).
- `checkAuth` (`McpServlet.java:151`).
- `BMcpPlatformService.getRegistry()` for tools.
- `McpProtocol.handle()` for dispatch.
- The `McpSessions` registry (post-refactor of §13.2 — sessions become typed).

What conflicts:
- **None** at the URL level.
- **Session lookup** — if the registry is shared, a Streamable session and an SSE session must have non-colliding sessionIds. UUID-v4 ensures this trivially.
- **`McpSession.outgoing` queue** semantics — only used by SSE. A Streamable session that doesn't open a server-push GET wouldn't use the queue at all (or would be an empty/unused field).

Existing SSE clients keep using `/sse` + `/messages?sessionId=…`. New clients use `/mcp` with `Mcp-Session-Id`.

**Rank: Clean addition** — backward compatibility is naturally achieved by adding new endpoints, not modifying old ones.

### 13.7 Dependencies for HTTP streaming primitives — already present. **Clean addition**

We already use:
- `javax.servlet.http.HttpServletRequest/Response` for request/response (`McpServlet.java:23-24`).
- `PrintWriter` for chunked write + flush (`McpServlet.java:21`, used at `:74`, `:79`, `:93`, `:100`, `:140`).
- `resp.setHeader(...)`, `resp.setStatus(...)`, `resp.setContentType(...)` for header control.
- `req.getInputStream()` for reading the request body (`McpServlet.java:177`).
- `BufferedReader` for parsing bodies (`McpServlet.java:176`).

For Streamable HTTP we'd additionally need:
- **Chunked transfer encoding**: enabled implicitly when `setContentLength` is *not* called and `Transfer-Encoding: chunked` is set by the container. We already do unspecified-length writes for SSE (which is just chunked under the hood) and that works on Niagara's Jetty.
- **`X-Accel-Buffering: no`** for SSE — already used (`McpServlet.java:69`); same for Streamable HTTP streaming responses.
- **`Mcp-Session-Id` header read/write** — `req.getHeader("Mcp-Session-Id")` and `resp.setHeader("Mcp-Session-Id", ...)`. Standard servlet-spec calls, no new dependency.
- **`Last-Event-ID` header** for resumption — same, standard header.

**Rank: Clean addition** — Niagara's Jetty + servlet-3.1 supplies everything Streamable HTTP needs.

### 13.8 Java 8 / future-Java for new code — Java 8 only. **Clean addition (with constraint)**

Confirmed in §1.5: the existing code is fully Java 8 compatible (no `var`, no lambdas, no switch expressions). The build script is Java-8 by Niagara plugin default.

For new code:
- `CompletableFuture` (Java 8) — available.
- `Map.of(...)`, `List.of(...)` (Java 9+) — **not available**, use `Collections.singletonMap`, `Arrays.asList`.
- Lambdas, streams, method references (Java 8) — available; we'd be the first place to use them.
- Records (Java 14+), pattern matching (Java 16+), text blocks (Java 13+) — not available.

For Streamable HTTP we don't strictly need anything beyond Java 8. If we want async tool calls with `CompletableFuture` for progress notifications mid-stream, Java 8 is enough.

**Rank: Clean addition (with constraint)** — write Java 8, period.

### 13.9 Doc drift — needs cleanup before next release. **Refactor needed (cosmetic)**

The bulk-rebrand done before v0.1.0 produced two known doc-drift artifacts:

- `_SMOKE_TEST.md:54` says *"исходный `niagaramcp-rt.jar` был подписан `BCC.RSA` (niagaramcp enterprise CA)"* — the rebrand mechanically replaced "BCControl" with "niagaramcp", producing a phrase that no longer makes historical sense (the original BCC CA was BCControl's, not "niagaramcp's").

These are not blockers for Streamable HTTP work but should be fixed in a small doc-cleanup commit before/with the next release, lest they accumulate.

**Rank: Refactor needed (cosmetic)**.

### 13.10 SSE-related dead code referenced in old review — partially closed. **No action**

`_CODE_REVIEW.md:118-122` listed several pieces of dead-code or unused API:

## §14 — Cannot-answer follow-ups

These questions appeared in the recon brief or arose during inspection but cannot be settled by static analysis. Each is deferred to a runtime test against a live Niagara station.

1. **Actual URL the servlet ends up at**.
   The static answer is `https://<station-host>/niagaramcp/sse` and `/niagaramcp/messages` (per §4). But the *full* URL depends on station port (typically 4911 for Foxs / 443 for HTTPS), bound interface, and reverse-proxy fronting. Verify with: `curl -k -v https://localhost:4911/niagaramcp/sse -H "Authorization: Bearer ..."` from the station host.

2. **Behaviour under concurrent SSE connections** — specifically, does Niagara's Jetty pool block accepts when all worker threads are parked in `session.poll()`?
   Static read: yes, this would happen above pool-size. Live verification: open N+1 SSE connections and observe the (N+1)th block until one of the others returns. Need a concurrent client.

3. **Tool survival across station restart**.
   Static read: `serviceStarted()` re-creates the registry from scratch on every start (`BMcpPlatformService.java:101-107`), and `serviceStopped()` clears `INSTANCE` and closes sessions. So tools are recreated, sessions are not preserved. A client must reconnect after a restart. Confirm by restarting the station and observing 404 on the previous session's POST.

4. **Whether `BControlPoint.get("out")` returns null for detached/null points or throws**.
   Code at `ReadPointTool.java:71-73` handles `null` defensively. Static read suggests `get()` returns null for missing slots. Behaviour for transiently-disconnected points (driver returning null vs throwing) needs a live driver to probe.

5. **`BOrd.make(query).get()` blocking time on slow drivers**.
   Already noted in `_CODE_REVIEW.md:145`. Empirical measurement requires a slow driver and instrumentation.

6. **Whether `org.eclipse.jetty.servlets.CrossOriginFilter` is on the runtime classpath**.
   Declared in `web.xml:15`. If missing at runtime the container logs `ClassNotFoundException` at servlet-init. Static check would require unpacking `web-rt.jar` and confirming Jetty's bundled class — `_SMOKE_TEST.md:163` already deferred this.

7. **Does the Streamable HTTP transport need a separate Niagara permission?**
   Probably no — `NETWORK_COMMUNICATION` and `UNAUTHENTICATED_ACCESS` are sufficient. Confirm by attempting to load a v0.2 module on a station with strict permissions and observing the load log.

8. **Performance of the bounded queue under burst**.
